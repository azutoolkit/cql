## [Unreleased]

### Upgrade notes

Behaviour changes an upgrading application may need to act on (details under Changed, Removed and Fixed):

- **Opt-in diagnostics.** The performance monitor and the per-request query cache are off by default; turn them on with `config.monitor_performance = true` (or `CQL::Performance.enable_monitoring`; the monitor also turns itself on with `CRYSTAL_ENV=development`) and `CQL::Cache::RequestQueryCacheHelper.start_request`. SQL logging is on only when development is named (`CRYSTAL_ENV=development` or `config.env = "development"`), or with `config.sql_logging = true`; an unset `CRYSTAL_ENV` no longer turns it on, and logged SQL no longer includes bound values.
- **Deletes.** `dependent:` options now run when the parent is deleted. `delete_all` on a query deletes in one statement when the model has no destroy callbacks and no `dependent:` associations. SoftDeletable `Model.delete_all`/`restore_all` return a count (`Int64`) instead of records.
- **Transactions.** A transaction opened inside another is a SAVEPOINT on the same connection: an inner block no longer commits on its own.
- **Queries.** `count` ignores `order` and respects `limit`/`offset`. `QueryBuilder#select(:a, :b)` returns `Model::Row` records; `where { }`, `join { }`, `left { }` and `right { }` return a new builder instead of also changing the receiver. `each` takes a block and returns `nil`. `reorder`, `unscope` and `from` replace a clause collection instead of emptying the one you may hold.
- **Errors.** `Insert`, `Update` and `Delete` raise `ArgumentError` for an unknown column (it was `KeyError`).
- **Validation.** `save` on a new record validates once, before `before_save`; values set in `before_save`/`before_create` are no longer validated.
- **Schema.** `timestamp`/`timestamps` columns are created as `TIMESTAMP` (`DATETIME(3)` on MySQL) instead of `DATE`; existing tables keep `DATE` until altered. Declared indexes are now created, with names `idx_<table>_<columns>`; on MySQL, creating the same tables twice raises.
- **Shared primary keys.** A has_many or has_one whose `foreign_key` is the target's primary key no longer compiles (it never worked); declare `belongs_to` from the target instead. Soft deleting an already soft-deleted record is now a no-op that keeps its first `deleted_at`.
- **Mass assignment.** `attributes(...)`, and so instance `update!(attrs)` and `save` after it, no longer assign the primary key: a request-supplied `id` (or custom key column) can no longer re-point a record at another row. Set the key with `id=`. `Model.from_hash` ignores the key too unless given `with_primary_key: true` (for trusted data: a record built with a key saves as an UPDATE of that row). Constructors (`Model.new(**params)`, `build(**params)`) are unchanged.
- **Primary keys.** A table keyed on a column other than `id` is declared on the model with `db_context Schema, :table, primary_key: :col`. A many_to_many target keyed that way must declare it (the join used the schema's key before), and with `CQL_VALIDATE_SCHEMA_MAPPINGS=1` a model whose key differs from its table's declared primary key raises `SchemaMappingError`.
- **Removed APIs.** `Dialect#format_insert_values`, the PostgreSQL driver's `ResultSet#result`, and the parent-ids argument of the generated `_preload_<name>` methods.
- **Models without `db_context`.** The typed query DSL (`where { }`, `joins`, `Model::Columns`, `Model::Row`) is now generated for every model, so a model that defines its own `Columns` or `Row` of another kind clashes. `CQL_VALIDATE_SCHEMA_MAPPINGS=1` also validates models whose schema was inferred; models with no resolvable schema are skipped. `Model.schema` of a model whose schema cannot be resolved raises `CQL::ActiveRecord::SchemaMappingError` (it was `NilAssertionError`), and `Model.table` no longer raises. `CQL_TABLE_NAME` and `CQL_SCHEMA_CONTEXT` are defined only for the arguments `db_context` was given.

### Added

- `db_context` is optional. A model without it maps to the table named after its type, underscored and pluralized (`User` => `:users`, `OrderItem` => `:order_items`, `Category` => `:categories`, `Box` => `:boxes`; only the last namespace segment counts, and an irregular plural such as `Person` needs `db_context table: :people`), and to the schema whose `CQL::Schema.define` block declares that table, found at compile time in the model's enclosing namespaces or at the top level. `db_context` also takes one argument alone: `db_context table: :people` (schema inferred) or `db_context schema: AppDB` (table inferred); `db_context AppDB, :users` is unchanged, and `primary_key:` combines with either one-argument form or stands alone (`db_context primary_key: :label_no`). When no define block declares the table, or several do, `Model.schema` raises `CQL::ActiveRecord::SchemaMappingError` on its first call and the model still compiles. Only literal `table :name` calls written directly in a define block are seen, not tables added with `Schema.new` and `.table`, by helper macros or inside `{% if %}`/`begin`, and a `private` schema constant in a namespace cannot be referenced: use `db_context` there and in multi-database apps. See docs/how-to/models/define-model.md.
- `db_context Schema, :table, primary_key: :label_no` maps a model's `id` to another primary key column (default `:id`), and `Model.primary_key_column` returns it. Loading rows, `attributes`, `Model.find`/`find?`/`find!`, `QueryBuilder#find`, `ids`, `none` and creating a record (`create!`, `save` on a new record, generated UUID/ULID keys) use the declared column. So do updates (`update!`, `update_by`, `save` on a persisted record including `DirtyTracking`'s changed-columns update, `touch`, `touch_all` and optimistic locking; `update!(record)`, `update_by` and the locked update leave the key column out of `SET`) and deletes (`delete!`, `delete_ids`, soft delete, `restore!`, `restore_all` and `force_delete!`). many_to_many targets (loading, `find`/`find_by`/`exists?`, and `dependent: :delete_all` on soft-deletable targets) use the target model's `primary_key_column`. So do `belongs_to` preloads, has_many `delete(id)` and `ids=` on a custom-keyed target, and typed `joins` ON conditions (`labels.label_no = stickers.label_no`). So do `after_cursor`/`before_cursor` and `insert_all`/`upsert_all` (generated UUID/ULID keys fill the declared column, and an upsert keeps the existing row's key and `created_at`), and the typed query DSL's `id` (`where { id == 7 }`, `order_by(id:)` and `select(:id)` use `labels.label_no`; `where(id: ...)` hashes still name a literal column). On PostgreSQL and CockroachDB, `Insert#last_insert_id` (and so `Repository#create`) returns the table's declared primary key column instead of always `id`; `Insert#returning_primary_key_sql` returns that statement as `{sql, params}` without changing the insert. New `QueryBuilder#where_primary_key(key)` filters on the declared key: `=` for one key, `IN` for an array, and no rows for an empty array; UUID keys are bound as text. `find!` names the key column in its error (`No records found with label_no=99`). `none` now matches no rows with `WHERE 1 = 0` for every model instead of comparing `id` to `-1`, which PostgreSQL rejects on a uuid column. `attributes(hash)` and `attributes(**attrs)` now match keys by column name, so UUID-keyed models accept `:id` (no longer `:_id_storage`) and ignore a value that is not a valid UUID, and a model with a custom key takes its column name (`label_no:`), not `id:`.
- has_many generates `insert_<name>_all(rows, batch_size: nil)`: inserts rows of column values (hashes or named tuples) as associated records through the target's `insert_all`, with the foreign key set to the parent's id on every row (replacing any given), and returns how many were inserted. Like `insert_all` it runs no validations or callbacks and builds no records; `create_<name>` is unchanged. See docs/how-to/relationships/has-many.md.
- `CQL::ActiveRecord::DirtyTracking`, an opt-in module: a record remembers its column values as last loaded or saved and reports `changed?`, `changes` (`{old, new}` per attribute), `attribute_changed?(name)` and `changed_columns`; `update!` and `save` then send only the changed columns, so a column another writer changed is left alone, and send no UPDATE (and leave `updated_at` alone) when nothing changed. Callbacks still run; what an `after_save`/`after_create` callback changes stays pending for the next save, and a `before_save` change to an otherwise unchanged record is stamped with `updated_at`. Changes are found by comparing values, so setters, `attributes(...)` and instance variable writes all count. With `OptimisticLocking`, a locked `update!` of a changed record still sends every column, and an unchanged one sends nothing and keeps its version. Include it after `Model` (the other order fails to compile). Models without the module are unchanged. See docs/how-to/models/dirty-tracking.md.
- `preload` loads `has_one` associations (`User.preload(:profile).all`) with one query per chunk of parent ids. Associations declared with `cache: false` are not preloaded, and preloading a `has_one` whose target has no foreign key attribute raises `ArgumentError`. A parent with several children gets an arbitrary one, as with the lazy reader.
- `preload` loads `belongs_to` associations (`Post.preload(:user).all`): one query per chunk of distinct foreign keys instead of one lookup per record when the association is read. Associations declared with `cache: false` are not preloaded. Records that share a target share one preloaded instance.
- `Model.upsert_all(rows, on_conflict:, update: nil, batch_size: nil)` inserts like `insert_all` and updates the rows whose `on_conflict` columns match an existing row: by default every inserted column except the conflict columns, `id` and `created_at` (so `updated_at` is refreshed); `update:` lists the columns to change and `[] of Symbol` leaves existing rows as they are. When the rows insert nothing beyond the conflict columns (and the table has no `updated_at`), existing rows are left unchanged. It returns the rows affected as the database reports them (MySQL counts a changed row twice and an unchanged row as zero). Conflict or update columns the rows do not insert, and `on_conflict: :id` with generated UUID/ULID ids, raise `ArgumentError` before any statement runs.
- `Model.insert_all(rows, batch_size: nil)` inserts an array of hashes or named tuples with multi-row INSERT statements and returns the number of rows inserted. Each statement binds at most the dialect's `max_bind_params` values unless `batch_size` sets the rows per statement, and a run of several statements commits or rolls back as one transaction. It runs no validations or callbacks and returns no records; it fills missing or nil `created_at`/`updated_at` columns with the current time, generates ids for UUID and ULID primary keys, and drops a nil `id` on other keys. Every row must have the same keys, each a column of the table, and `batch_size` may not bind more than `max_bind_params` values per statement, or it raises `ArgumentError` before any statement runs. See docs/how-to/data-operations/create.md.

- `CQL::ConnectionSource`: where a `Schema` gets its connections and transactions from. `CQL::DatabaseSource` (crystal-db's pool) stays the default; `CQL::Postgres::EngineSource` runs a schema on an `AsyncEngine`'s pool (`CQL::Schema.new(..., source: CQL::Postgres::EngineSource.connect(url))`), so models, queries, migrations, `schema.transaction` and `schema.with_connection` use the engine without `using(engine)`. `Schema#close` and `Schema#source` are new; a source for another adapter than the schema's raises `ArgumentError`; through the engine a connection that cannot be opened raises `DB::ConnectionRefused` (crystal-db raises it only for the first connect and `DB::PoolRetryAttemptsExceeded` for a lazy one, so code rescuing that class will not match) and a saturated pool `DB::PoolTimeout` (a closed pool raises `CQL::Postgres::PoolClosed`; there is no connect retry); `Schema#uri` of an engine-backed schema leaves out the engine's pool options (`pool_size`, `max_queries`, ...). Note: `Migrator#up` still runs each migration's statements on a second pooled connection (they are not inside the migrator's transaction; pool size 1 deadlocks), on both sources. See `docs/how-to/postgres-native/schema-on-engine.md`.
- PostgreSQL driver binary parameters (`binary_params=true`, off by default: measured faster for arrays and for statements with several parameters, about even for a single value; see the README) chosen per parameter from the server's `ParameterDescription` for int2/4/8, float4/8, bool, uuid, timestamp(tz), date, numeric, jsonb and arrays of them, falling back to the text form whenever there is no equivalent binary one; CockroachDB keeps float4 and numeric as text. Binary `COPY`: `Session#copy_in_binary` / `copy_out_binary` (and on `Connection`), which raise `ArgumentError` if the server runs the statement as text. `Session#encode` builds a parameter for the session's setting; `ParamEncoder.encode(value, binary)` defers one.
- PostgreSQL driver live verification: `script/tls-probes` (TLS refusal against real servers, asserting the pool does not retry), `script/pooler_probes.cr` (nine probes for any pooler) and `spec/postgres/blackhole_spec.cr` (hard close under TLS on a dead path); results for PostgreSQL 19rc1, PgBouncer 1.26.1 (also with client TLS, `sslmode=require` and `verify-full`), Odyssey 1.5.2, pgcat 1.2.0 and pgpool-II 4.3.7 are in the README. A server that resets the connection before answering a 3.2 startup (Odyssey) now falls back to 3.0 like one that closes it.
- Native PostgreSQL wire-protocol driver (`require "cql/postgres"`, also loaded by `require "cql"`): `CQL::Postgres::AsyncEngine` is a `CQL::Executor` (`query.using(engine)`, `engine.transaction`, `engine.pipeline`) with its own fiber-safe connection pool, startup/authentication (trust, cleartext, MD5, SCRAM-SHA-256), TLS and Unix sockets, simple and extended protocol with prepared-statement caching, binary results, `COPY`, `LISTEN`/`NOTIFY`, cancellation and statement timeouts, and typed `CQL::Postgres::ServerError` subclasses per SQLSTATE. Rows map into `all(as:)` and models through crystal-db's own interfaces. Bound values and passwords never appear in driver messages or telemetry. `Pinnable#using` (and the ActiveRecord query builder's) now also accepts any `CQL::Executor`. See the README section "Native PostgreSQL Driver", `playground/postgres_async_demo.cr` and `benchmarks/pg_wire_bench.cr`.
- PostgreSQL driver speaks protocol 3.2 and falls back to 3.0 (`NegotiateProtocolVersion`, or a rejected startup on older servers); `min_protocol_version` / `max_protocol_version` URL options pin the range, and cancel requests carry the server's (possibly 256-byte) secret key.
- PostgreSQL driver transactions take `isolation:`, `read_only:`, `deferrable:` and `synchronous_commit:` (a `SET LOCAL`; see the README for the durability trade-off) and offer `tx.savepoint { }`. The pool gains `pool_min_size`, `max_queries`, `max_idle_lifetime`, a per-connection `setup:` hook and a `reset:` statement; a transaction left open by a borrower is now rolled back and the connection reused instead of dropped.
- The native PostgreSQL driver is now the default crystal-db driver for `postgres://` and `postgresql://` URLs (`require "cql"` registers it; `cockroachdb://` is opt-in with `CQL::Postgres::Driver.register_cockroachdb` or `-Dcql_postgres_driver_cockroachdb`; a `pg` shard loaded first, or later, keeps serving `postgres`/`postgresql`), so `CQL::Schema` runs on it without the `pg` shard (schemas on `CQL::Adapter::CockroachDB` use the `postgres` name, so they follow the same rule). A `Schema` on the default driver was checked against PostgreSQL 18; see the next entry for the other servers. Server errors 42P05 and 26000 now say to try `statement_cache_size=0` behind a transaction-mode pooler.
- PostgreSQL driver compatibility, each checked against a real server: PostgreSQL 11 through 18 (`script/pg-matrix`), PgBouncer 1.22 in transaction and session mode (`script/pgbouncer-matrix`) and CockroachDB 24.3 (which answers an unknown protocol version with HTTP/2 bytes: `cockroachdb://` starts at 3.0 and any unrecognised first reply falls back to 3.0; its stale-plan error is recognised too). `-Dcql_no_postgres_driver` keeps the driver out of crystal-db's registry.
- PostgreSQL driver `ResultSet#result` is gone (rows now come from an iterator, so a `RowStream` can back a result set) and `ResultSet.new` takes `detached` positionally.
- PostgreSQL driver streaming: `engine.stream(query, fetch_size:)`, `Connection#stream` (a lazy `DB::ResultSet`) and `Session#stream` (a `RowStream` iterator) read large results through a portal `fetch_size` rows at a time; stopping early, errors between fetches, cancel and timeouts leave the session in sync (checked on PostgreSQL 16 and CockroachDB 24.3).
- PostgreSQL driver fix: with `statement_cache_size=0` the unnamed statement is now described without a Sync, so Parse/Describe and Bind form one request. Behind a transaction-mode pooler with several server connections they could land on different ones, failing with a parameter-count error or running another client's statement.
- PostgreSQL driver hardening: connection failures reach crystal-db's pool as `DB::ConnectionRefused` (so `retry_attempts` applies); a health-check ping and a timed-out request whose cancel is ignored now close the socket instead of blocking (`Session#ping(timeout)`, `Session#cancel_grace`); a `TransactionScope` raises `TransactionClosed` once its block is over; `inspect` of sessions, connections and pools shows no secrets; malformed pool options (`pool_size=abc`, `max_queries=many`, ...) raise `ArgumentError`; `Pool#close` wakes waiting fibers; `AsyncEngine.connect` picks the CockroachDB adapter for `cockroachdb://`; a server that closes the connection on a 3.2 startup falls back to 3.0. Telemetry carries no bound values unless `capture_params` is on. Telemetry now labels `WITH ... INSERT/UPDATE/DELETE` queries by the statement they modify (they were `select`) and skips leading comments; `RowStream#next` raises when called from another fiber; `TransactionScope` is a standalone class (no longer a `CQL::ConnectionExecutor`); `Config.number`, `Config.seconds` and `Config.whole` are public.
- PostgreSQL driver: a required TLS that cannot be had (the server declines, answers the SSLRequest oddly, or fails the handshake or certificate check) raises `CQL::Postgres::TLSRefused`, which is not an `IO::Error`, so crystal-db's pool does not retry it and the cause is not lost; dropping a connection closes the socket itself (no TLS close_notify that could block on a dead path); `RowStream#next` from another fiber raises `WrongFiber`; telemetry's statement labelling also understands `E'...'` strings; a server that hangs up during the SSLRequest or the TLS handshake stays a retryable `IO::Error`; a pool health-check ping waits at most `Session::PING_TIMEOUT` (5 seconds) even when `checkout_timeout` is longer.
- PostgreSQL driver fix: `Session#cancel` now ends a stream that still has rows to fetch. PostgreSQL ignores a cancel while no statement is running, which is the case between the fetches of a stream, so such a cancel used to be lost and the stream ran to the end; once the cancel has been delivered, the next fetch raises `QueryCanceled` (buffered rows are still delivered first), and a cancel still in flight when the stream ends is waited for.
- PostgreSQL driver cancel follow-up: every request, not only streams, waits for a `Session#cancel` that is still on its way before the session is handed on, and drops the session if it is not delivered within about twice `cancel_grace` (a cancel counts as delivered once written and the hang-up wait ended, even if the peer never hung up; a cancel begun while no request holds the session is not covered); a pool health-check ping on a session with a cancel pending reports it unhealthy; a cancel's own connect (name lookup included, not a Unix socket) and wait for the postmaster's hang-up are each capped at `cancel_grace` (`Session#cancel_grace` now also bounds those and the wait, not only the time between a timeout and the socket being closed); a `QueryCanceled` the driver raised itself (`CQL::Postgres::LocalCancel`) is no longer taken as the server's confirmation of a timeout cancel, so such a session is dropped instead of kept with a portal still open; a cancel that lands on a stream's cleanup is ignored.
- Typed model DSL: `Model.query.where { (age >= 18) & (status == "active") }` with bare column names typed to the column (unknown columns and type mismatches are compile errors), `order_by(created_at: :desc)` checked at compile time, `joins(:assoc) { ... }` / `left_joins`, `to_a`, and `Model.cql_columns` / `cql_association` metadata.
- Telemetry: `CQL::Telemetry.subscribe`, `alert_on_slow`, `log_queries`, `with_context` and an abstract `Tracer` for OpenTelemetry-style adapters; parameters are not captured unless `capture_params` is on.
- Transaction telemetry: `Telemetry.subscribe_transactions` / `unsubscribe_transactions` publish `TransactionEvent`s (Begin, Commit, Rollback with id, duration, `nested`, `error`) from `Schema#transaction`; `Telemetry.subscribed?(name)` and `next_transaction_id`. `Schema#pool_stats` returns a `CQL::PoolStats` (`open`, `idle`, `in_flight`, `max`) without checking out a connection. A manual `tx.rollback` followed by a normal return still reports Commit.
- Unified execution: every statement runs through `CQL::Execution.run`; `Schema#with_connection` and `query.using(connection)` pin an explicit connection (e.g. a transaction).
- Safe raw SQL fragments: `where("lower(name) = ? AND age > :age", "ada", age: 18)` on `Query`, `QueryBuilder`, models, associations, `Update` and `Delete`, plus `raw(...)` inside `where { }` blocks and `CQL.raw`. Values are always bound as parameters (arrays expand to `IN (?)` lists, `??` is a literal `?`, quoted text and comments are skipped); a value given in the wrong placeholder style raises instead of being dropped. The fragment text must be a literal, never built from user input. `nil` binds NULL (`name = ?` never matches it; use `IS NOT DISTINCT FROM ?`).
- Window functions: `query.window(:row_number, as: :dept_rank, partition_by: :dept, order_by: {salary: :desc})`, aggregates over a window (`window(:sum, :salary, as: :running, order_by: :id, rows: {:unbounded_preceding, 0})`), `lag`/`lead`/`first_value`/`last_value`/`ntile`/`rank`/`dense_rank`/`percent_rank`/`cume_dist` and ROWS/RANGE frames. Needs MySQL 8.0+ and SQLite 3.25+. On MySQL, avoid window function names (`rank`, `row_number`, ...) as aliases unless `quote_identifiers` is on.
- Upsert and bulk upsert: `insert.on_conflict(:email).do_update(:name, visits: 1)`, `.do_nothing`, and `insert.upsert(rows, conflict: [:email], update: [:name])` (`ON CONFLICT` on PostgreSQL/SQLite, `ON DUPLICATE KEY UPDATE` on MySQL). Not supported with `INSERT ... SELECT`. Needs SQLite 3.24+. On MySQL the conflict target is ignored: any unique key triggers `ON DUPLICATE KEY UPDATE`.
- CockroachDB: `CQL::Adapter::CockroachDB` (`cockroachdb://` URLs, opened through the PostgreSQL driver) with a dialect that inherits PostgreSQL's SQL (`Int32` columns are declared `INT4`, since CockroachDB's `INTEGER` is 64-bit); it shares PostgreSQL's query features, but `structure_dump` is unsupported. The CA path is passed as `sslrootcert`.
- Row locking `query.lock(:update | :share, skip_locked:, nowait:)` (PostgreSQL, MySQL, CockroachDB; SQLite raises `CQL::DialectError`), `distinct_on(:col)` (PostgreSQL, CockroachDB), `FULL` and `CROSS` joins (`full(:t) { |j| ... }`, `cross(:t)`; MySQL has no FULL JOIN).
- Predicates: `ilike` / `not_ilike` (native `ILIKE` on PostgreSQL, `LOWER()` comparison elsewhere), `not(...)` / `.not` on conditions, `count(:col, distinct: true)`.
- JSON: `col.json_eq(path, value)` (value at a key/index path compared as text) and `col.json_contains(json)` (PostgreSQL `@>`, MySQL `JSON_CONTAINS`; not on SQLite), with the path always bound as a parameter. Geospatial: `col.within_distance(longitude, latitude, meters)` (`ST_DWithin` on geography for PostgreSQL/CockroachDB, `ST_Distance_Sphere` with a long-lat point on MySQL 8.0.13+; the MySQL form is unverified against a live server and expects an SRID 4326 column).
- Set operations: `union`, `union_all`, `intersect`, `except` on queries and on each other (`CompoundQuery`), executable like any query. Operands with their own `ORDER BY`/`LIMIT` or nested set operations are grouped (derived tables on SQLite). Ordering the combined result is not supported yet. MySQL needs 8.0.31+ for `INTERSECT`/`EXCEPT` and 8.0.18+ for `EXPLAIN ANALYZE`.
- `query.to_sql(for: CQL::Adapter::Postgres)` renders SQL for another dialect without a connection, and `query.explain(analyze: false)` returns the database's execution plan (SQLite `EXPLAIN QUERY PLAN`, PostgreSQL/MySQL `EXPLAIN [ANALYZE]`).
- Common table expressions and derived tables: `query.with(:totals, subquery).from(:totals)`, `with_recursive(:tree, anchor) { |step| ... }` for `WITH RECURSIVE`, and `from(subquery, as: :alias)`. The CTE/subquery's selected columns (and aliased aggregates) are addressable in the DSL like any table. `with(:b) { |scope| ... }` builds a CTE that can read earlier ones, and `query.nested` gives subqueries access to the query's CTEs. Available on `CQL::Query` (not on `QueryBuilder`/models yet). Needs MySQL 8.0+ and SQLite 3.8.3+.
- `CQL::Executable`: one shared implementation of `all`, `get`, `each`, `to_sql` and `explain` (result cache and performance tracking included) for every executable statement.

### Changed

- Soft deleting a record that is already soft deleted is a no-op: instance `delete!` returns false without running callbacks, and `Model.delete_ids` and a query's `delete_all` (including `with_deleted.delete_all`, record by record or in bulk) only stamp rows whose `deleted_at` is NULL, so a row keeps its first deletion time and the returned count is of rows this call deleted. Before, they were stamped again and counted. A parent's `dependent: :destroy` counts such children as already deleted.
- **Breaking:** has_many and has_one whose `foreign_key` is the target's primary key (a shared primary key) now fail to compile with an error that says so. They never worked: `create!` let the database assign the target's key, so it never equalled the parent's id, and has_one compiled but failed when used.
- **Breaking:** `attributes(Hash)` and `attributes(**)` ignore the primary key (`id`, or the column named by `db_context ..., primary_key:`). Before, `record.attributes(params)` with an `id` re-pointed the record, so a following `save` or `update!` overwrote another row. `id=` still sets it, and `Model.from_hash` ignores it unless called with `with_primary_key: true`.
- With `CQL_VALIDATE_SCHEMA_MAPPINGS=1`, a model whose primary key column (default `id`) differs from the primary key its schema table declares now raises `SchemaMappingError`, suggesting `db_context ..., primary_key: :col`; the key column's type is checked against the model's `id` type. An app running with the flag and a default-`id` model on a table whose `primary` column has another name must add `primary_key:`.
- many_to_many targets are joined on the target model's `primary_key_column` (default `id`) instead of the primary key declared in the target's schema table. A target table keyed on another column must declare it on the model with `db_context Schema, :table, primary_key: :col`; otherwise the join uses `id` and fails with `Column 'id' not found` (such a model also loaded `id` as nil, so it was not usable end to end before).
- With `quote_identifiers: true`, each table and column keeps its quoted name per dialect (`CQL::QuotedNameCache`) instead of being quoted (a `gsub` and a new String) every time a query names it, an alias equal to its table's name reuses the table's quoted name, and `quote_identifier` skips the `gsub` when the name has no quote character. A quoted simple `to_sql` goes from about 606k to 758k ops/s (2.24 to 1.89 kB) and a quoted join with order and limit from 365k to 422k, closing most of the gap to unquoted SQL. The cache is one immutable object per table or column, so it needs no lock; another dialect or a renamed table or column is quoted afresh. It adds no column-like methods to tables, so columns of any name stay reachable in the query DSL. `benchmarks/sqlite_bench.cr` has a new `quoted simple where by id` workload.
- `Query#build` builds the select list, GROUP BY and ORDER BY in the types the statement holds instead of building them and copying them (`map`, `to_h`, `transform_keys`) into it, and checks the explicit select list for a repeated column with a pass over its few entries before deduplicating it through a hash. In `benchmarks/sqlite_bench.cr`, `join with order and limit` goes from about 432k to 498k ops/s (4.27 to 3.73 kB per query), simple `to_sql` from 835k to 865k (1.97 to 1.89 kB) and `where.order.first` allocates 4.27 kB instead of 4.61 kB. The SQL is unchanged, and a column selected twice under the same alias is still selected once.
- The native PostgreSQL driver spends about a fifth less CPU per query: Bind, Execute and Sync are written straight into the connection's output buffer (their length filled in afterwards) instead of each allocating a message buffer that is then copied, 16- and 32-bit protocol fields are written without `IO#write_bytes` (which reversed a `StaticArray` per field), and a prepared-statement cache hit is one hash lookup instead of a delete and re-insert of the SQL text. A `Model.find` against a local PostgreSQL 16 goes from about 69.5k to 54.7k client instructions; with the server's round trip dominating, `pg_wire_bench`'s 8-fiber workloads are about 2-3% faster. Messages that can fail to encode (for example a NUL byte in SQL text) still go through a buffer, so a failure leaves nothing half-written.
- Multi-row INSERT is generated faster: the generator writes the VALUES list straight into the statement and binds each row's values in one step (instead of collecting a placeholder per value and having the dialect build the list as a separate String), SQLite and MySQL return their `?` placeholder without a hash lookup, and a row that lists its keys in the first row's order is placed without a column lookup per value. In `benchmarks/sqlite_bench.cr`, `insert 500 rows` goes from about 10.0k to 15.6k ops/s (334 to 298 kB per statement). The SQL is unchanged.
- The SQL generator writes every clause of a SELECT (the select list's column references, FROM, JOIN, WHERE, GROUP BY, HAVING, ORDER BY, CTEs, subqueries), its conditions (comparisons, `NOT`, `IN`, `BETWEEN`, `EXISTS`, `IS`, raw fragments) and the SET list, table and WHERE of UPDATE, DELETE and INSERT straight into the statement's one string builder, instead of each node returning a String that its parent copies. In `benchmarks/sqlite_bench.cr`, simple `to_sql` goes from about 667k to 846k ops/s (2.79 to 1.97 kB), `10-condition where` from 244k to 328k (8.54 to 5.89 kB), `join with order and limit` from 357k to 438k (5.61 to 4.27 kB), `update!` from 303k to 338k and `ArUser.last` from 322k to 364k. The SQL is unchanged, and each node's public `visit(node) : String` still returns its SQL.
- `Model.create!` on PostgreSQL and CockroachDB reads the new row from the INSERT's `RETURNING` clause instead of inserting and then running `find!`, so it takes one round trip instead of two (the stored row, with database defaults, is still returned). Against a local PostgreSQL 16, `create!` goes from about 3.8k to 5.3k ops/s (6.31 to 4.84 kB per call). Models that define their own `self.query` and subclasses of models still read the row back through `self.query`; SQLite and MySQL are unchanged. Because the row no longer goes through `self.query`, a SoftDeletable model created with `deleted_at` set is returned instead of raising `DB::NoResultsError` after the insert, and the `:insert` telemetry event of such a `create!` reports no `rows` count (as integer-key `create!` on PostgreSQL already did). New: `Dialect#supports_returning?` (it replaces the adapter check in `Insert#last_insert_id`) and `Insert#get(as:)`/`get!(as:)`, which run an insert and read the row its `back` columns return; they raise `CQL::DialectError` on SQLite and MySQL, and `ArgumentError` without `back` columns, before inserting.
- `CQL::Query#first` renders the query with `LIMIT 1` (`Query#build` takes an optional `limit:`) and runs it as a `CQL::PreparedSelect` on the same executor instead of cloning the whole query to set the limit. In `benchmarks/sqlite_bench.cr`, `ArUser.last` goes from about 284k to 321k ops/s and `where.order.first` allocates 5.83 kB instead of 6.44 kB.
- `Model.find`/`find?`/`find!` render their SQL once per model and reuse the statement, binding only the id (the statement, never the result, is cached). In `benchmarks/sqlite_bench.cr`, `ar: find by id` goes from about 306k to 1.05M ops/s (4.45 kB to 480 B per call). Models that override `self.query` and subclasses of models keep rendering per call, so per-call scopes (for example a tenant filter) still apply; SoftDeletable's filter is reused, and the statement is re-rendered if `db_context` points the model at another schema or table or `Schema#alter` changes its columns (new `Table#columns_revision`). New: `CQL::PreparedSelect`, `CQL::StatementTemplate` and the `CQL::ActiveRecord::StaticQuery` annotation that marks CQL's own `self.query` definitions.
- `CQL::Query` allocates its rarely used clause collections (`order_by`, `group_by`, `joins`, `select_expressions`, `column_aliases`, `ctes`, `derived_tables`, `distinct_on`) on first use, and `clone` copies only the ones that hold something. Their getters keep returning a mutable collection (allocating it on first call); the new `order_by?`, `group_by?`, `joins?`, `select_expressions?`, `column_aliases?`, `ctes?`, `derived_tables?` and `distinct_on?` tell whether one holds anything without allocating. `reorder`, `unscope` and `from` now replace a cleared collection instead of emptying it in place, so a collection fetched before one of those calls is no longer the query's. `Query.new` goes from 656 to 304 bytes and `clone` from about 400 ns / 912 B to 270 ns / 624 B; in `benchmarks/sqlite_bench.cr`, `ar: find by id` goes from about 264k to 307k ops/s and `where.exists?` from about 308k to 361k ops/s. SQL is unchanged.
- With the performance monitor on, a query's log message is formatted only when its log level is emitted (it used to be pretty-printed with eight regex passes even when the level dropped it), and `SQLUtils.normalize_sql` keeps the normalized form of each SQL text (at most 512, oldest first) instead of re-running its regex on every query. A tracked query with repeated SQL text whose log line is filtered out goes from about 7.5 µs to 0.6 µs (a `Benchmark.ips` of `Monitor#track` with logging at `warn`).
- An unset `CRYSTAL_ENV` no longer turns on SQL logging (and with it the performance monitor) in `CQL.build_schema`: the default is on only when development is named, with `CRYSTAL_ENV=development` or `c.env = "development"`. An unset environment still gets the other development defaults. Logging every query cost about 12-14 µs per query (48 µs with stdout on a terminal), which made apps started without `CRYSTAL_ENV` several times slower on simple reads; set `CRYSTAL_ENV=development` or `c.sql_logging = true` to keep it.
- Raw SQL fragments (`where("lower(name) = ?", value)`) are parsed once per distinct SQL text and the parsed template is reused (at most 512 kept, oldest dropped first), so building one goes from about 720 ns to 130 ns (a `Benchmark.ips` of `Expression::Raw.build` with two placeholders). Values are still bound per call.
- Multi-row `CQL::Insert#values(rows)` places each later row's values through a column index built from the first row, instead of building per-row pairs, name lists and a set difference and reordering with a linear search per column (O(rows × cols) instead of O(rows × cols²)). In `benchmarks/sqlite_bench.cr`, `insert 500 rows` goes from about 4.9k to 8.8k ops/s (529 to 334 kB per statement). Rows with an extra, missing or different column still raise `ArgumentError`.
- Chained `AND`/`OR` conditions are written into one string builder instead of each level building its own string and copying its children into it, so the bytes copied grow with the number of conditions rather than its square. In `benchmarks/sqlite_bench.cr`, `10-condition where` goes from about 177k to 214k ops/s (12.1 to 9.25 kB per query); the SQL is unchanged.
- Building the SELECT list is linear in the number of columns: an implicit select no longer scans the list for duplicates before adding each column or builds an `alias.column` string per column to deduplicate it, and the generator writes the list straight into the SQL. In `benchmarks/sqlite_bench.cr`, `simple where by id` goes from about 377k to 490k ops/s (4.38 to 3.3 kB per query) and `ar: find by id` from about 213k to 245k ops/s; the SQL is unchanged.
- **Breaking:** association `dependent:` options now take effect when the parent is deleted (see Fixed). has_many and has_one apply a strategy only when `dependent:` is declared; without it, deleting the parent leaves the associated rows to the database's foreign keys, and the old defaults still apply to `clear`, `create_<name>` and `delete_<name>` (has_many `clear` nullifies, has_one replaces and deletes with `:destroy`). many_to_many always deletes the owner's join rows when the owner is deleted, and with `dependent: :destroy` or `:delete_all` its targets too. A soft-deletable model applies the strategies on `delete!` as well as `force_delete!`; `restore!` does not undo them. `delete_all` on a query loads and deletes record by record when the model declares a `dependent:` association or a many_to_many (as it already did for destroy callbacks), and that record-by-record path now runs in one transaction; on such models it is slower than the single-statement bulk path. SoftDeletable's `Model.delete_by!` also runs in one transaction. New class method: `Model.delete_applies_dependents?`. has_one and many_to_many reject an unsupported `dependent:` value at compile time. The no-op `handle_association_dependencies` instance method is removed.
- `save` on a new record runs the model's validations once, before `before_save`; it used to run them a second time inside the instance `create!` it called, after `before_save` and `before_create`. Values those callbacks set are therefore no longer validated (set them in `before_validation` instead), and `save` no longer calls an instance `create!` that a model overrides. Calling `create!` on an instance directly still validates.
- many_to_many `exists?(**attributes)`, `find(**attributes)` and `find_by(**attributes)` run one statement (`WHERE <attributes> AND id IN (SELECT <target key> FROM <join table> WHERE <owner key> = ?)`) instead of reading the join table and then querying the targets by id. They keep the target's default scope (soft-deleted targets are skipped) and return each target once. `find` and `find_by` with no attributes return the associated targets instead of raising, and `exists?` with no attributes means "not empty".
- The generated `_preload_<name>` class methods take only the records (`_preload_posts(records, chunk_size)`); the parent ids argument is gone. has_many preload binds UUID parent ids as strings, so a has_many on a UUID-keyed model compiles.
- **Breaking:** SoftDeletable `Model.delete_all` and `Model.restore_all` return the number of records soft deleted or restored (`Int64`) instead of the array of records, and run in bulk: `delete_all` goes through the query's `delete_all` (one UPDATE of `deleted_at` per chunk of ids unless the model declares destroy callbacks), and `restore_all` clears `deleted_at` with one UPDATE per chunk instead of saving each record.
- `delete_all` on a query (`User.where(...).delete_all`) no longer loads and deletes record by record when the model declares no `before_destroy`/`after_destroy` callbacks: it reads the matching ids with one SELECT and deletes them with one `DELETE ... WHERE id IN (...)` per chunk of the dialect's bind limit, and a soft-deletable model sets `deleted_at` with one UPDATE per chunk. Models with destroy callbacks keep the per-record path; a model that only overrides the instance `delete!` is deleted in bulk, so declare a destroy callback if that code must run. The result is now the number of rows deleted (it used to be the number of records loaded, which counted rows repeated by a join and records whose `delete!` failed; the per-record path now counts only successful deletes). The query's order is dropped unless it has a limit or offset. New class methods: `Model.destroy_callbacks?`, `Model.delete_ids(ids)` and `Model.stored_id_type`. `QueryBuilder#ids` now selects only the id column even when the query selects others.
- has_many `ids=` assigns the parent with one `UPDATE ... WHERE id IN (...)` (per chunk of the dialect's bind limit) instead of one UPDATE per id, and many_to_many `clear_with_delete` on a `dependent: :delete_all` collection deletes the targets with one `DELETE ... WHERE id IN (...)` per chunk instead of one per record (soft-deletable targets are soft deleted as `Target.where(...).delete_all` would, see Fixed). Repeated ids are sent once.
- has_many preload splits its `WHERE fk IN (...)` into one query per chunk of parent ids, so preloading more parents than the database's bind-parameter limit works (it used to fail with "too many SQL variables" on SQLite or a driver or protocol error on PostgreSQL and MySQL). The limit comes from the new dialect hook `max_bind_params` (32767 by default, the most both PostgreSQL drivers accept, 999 for SQLite, the lowest default of any SQLite build); up to that many distinct parents still preload in one query. Chunks are separate statements, so outside a transaction they may see different snapshots.
- `each` on a query, a model query and a model class (`CQL::Executable#each(as:)`, `QueryBuilder#each`, `Model.each`) takes a yielding block, so `break` works, and returns `nil`. It still reads the rows and releases the connection before yielding; iterate large results with `find_each`, which pages by primary key.
- `find_each` and `find_in_batches` page by primary key (`WHERE pk > ? ORDER BY pk LIMIT n`) instead of LIMIT/OFFSET, so each batch is an index seek rather than a rescan, and deleting an already-visited row mid-iteration no longer skips a later row. They no longer keep a set of processed ids or stop after 10,000 batches, and a non-positive `batch_size` raises `ArgumentError`. A query with its own `order`, an explicit select, DISTINCT, GROUP BY or HAVING (or a table without a primary key) still pages by OFFSET in that order, now with the primary key appended as a final tiebreaker (except for grouped queries, DISTINCT ON, and DISTINCT over an explicit select) so rows tied on the sort keys page deterministically. Paging by primary key, each row is still yielded once across a join; the OFFSET path no longer de-duplicates, so an ordered or shaped query over a join yields a record once per joined row. Batching ignores a query's `limit` and `offset`, as before.
- has_many association checks read at most one row: `<assoc>_any?` and an unloaded collection's `empty?` and `exists?(**attributes)` run one `SELECT <pk> ... LIMIT 1` instead of a `COUNT(*)`, loading every associated record, or loading all ids and then the records. A loaded collection still answers `empty?` and `<assoc>_any?` from memory. `exists?` now raises for an attribute the target table does not have, even when the parent has no records (it used to return `false` without querying). An unloaded `empty?` no longer loads (and keeps) the collection, so iterating afterwards runs its own query. `exists?` with no arguments means "not empty". `ManyCollection#exists?` is unchanged in this release.
- `exists?` and `any?` (on a query or a model) select one primary key with `LIMIT 1` instead of running a full `COUNT(*)`, and `many?` reads at most two rows. The rows are stepped over by the new `CQL::Executable#returns_rows?(count)`, which reads no column. `Model.exists?` shares the query builder's path. Queries with an explicit select, DISTINCT or grouping count a window capped at one or two rows, so `many?` on a grouped query now means two or more groups (it used to read the first group's row count). A negative `limit` is treated as no limit.
- `Model.last` and `query.last` fetch one row (`ORDER BY ... DESC LIMIT 1`, reversing the query's order, or the primary key when it has none) instead of loading every matching row and taking the last. Queries with `limit`, `offset`, `group`, `having`, `distinct` or an aggregate select keep the old behaviour. An unordered `last` returns the row with the highest primary key (for random UUID keys that is not insertion order), and rows tied on the `ORDER BY` are resolved by the primary key.
- With the performance monitor on, each query's SQL is normalized once (in a single regex pass instead of four) and shared by the profiler and the N+1 detector. `QueryProfilerInterface#record_query` and `NPlusOneDetectorInterface#record_query` take an optional trailing `normalized_sql : String? = nil`; custom implementations of those interfaces must accept it.
- `CQL::Adapter#dialect` returns one shared, stateless dialect instance per adapter instead of a new one for every `to_sql` (simple queries generate about 30% faster), and Postgres placeholders come from a precomputed table. The protected `DialectHelpers#cached_sql` helper and its per-instance cache are removed; custom dialects that called it must memoise themselves without instance state.
- The per-request query cache (`CQL::Cache::RequestQueryCache`) tracks only between `start_request` and `end_request`, or after an explicit `enabled = true`. Before, it was on for every SELECT in the process (an MD5 of the SQL and parameters under a global lock), grew without limit when no request was active, and `config.cache.on` with `request_cache` switched it on globally. `end_request` now turns tracking off again. Statements are keyed by their SQL text plus a hash of the parameters, so no parameter values are kept in memory (the old string key could make different statements collide), the `max_size` cap applies to tracked statements and evicts the oldest, and `stats` keeps the same keys. Tracking stays on while any request is active: the cache is process-wide, so overlapping requests share it and their stats are combined; it turns off once the last active request ends.
- The performance monitor (query profiler and N+1 detector) is now opt-in: it costs several regex passes and two global locks per query, and it was on by default outside the test environment. Turn it on with `CQL::Performance.enable_monitoring`, `CQL.configure { |c| c.monitor_performance = true }` (the option existed but was never read), `CQL_MONITORING_ENABLED=true`, or `CQL_ENV`/`CRYSTAL_ENV=development`; production no longer enables it implicitly, so apps reading `CQL::Performance.metrics` or health checks must opt in. SQL logging runs through the monitor, so `CQL::Performance.enable_sql_logging` enables it too, as does `CQL.build_schema` when `sql_logging` is on (setting `sql_logging = true` in `CQL.configure` alone does not); With the default configuration, enabling the monitor (including through SQL logging) also turns on the profiler, which keeps slow-query records, including bound parameters, in memory. Enabling is one-way: `monitor_performance = false` does not switch off a monitor enabled elsewhere, and `CQL.reset_config!` does not reset the monitor.

- **Behavior change:** `QueryBuilder#select(:a, :b)` now returns a builder whose results are `Model::Row` records (unselected columns are `nil`) instead of hydrating a full model that failed for non-nilable attributes. `QueryBuilder#where { }` now yields typed bare columns; `ids` goes through the executor. Use `Model.query.select(...)` results as `Model::Row`, not `Model`.
- **`QueryBuilder#where { }`, `join { }`, `left { }`, `right { }` return a new builder** like every other builder method; they no longer also mutate the receiver. Use the returned value.
- `NOT (...)` conditions are always parenthesized (`NOT a AND b` negated only `a`).
- `Insert`/`Update`/`Delete` raise `ArgumentError` ("Column x not found in table") for an unknown column; they used to raise `KeyError`, so a `rescue KeyError` around them must change.
- `Query#first` no longer temporarily rewrites the query's limit; it runs a copy with `LIMIT 1`.
- Aggregates accept `as:` (a Symbol) for a select-list alias: `count(:id, as: :n)`.
- Opt-in identifier quoting: `CQL::Schema.define(..., quote_identifiers: true)` quotes table, column and alias names (double quotes, backticks on MySQL). Default is off, so generated SQL is unchanged. Quoting covers queries and DML only; DDL (`build`, migrations, `alter`) is not quoted yet.

It was the generator's internal hook for the VALUES list, took the generator's flat placeholder list, and had three identical implementations; the generator now writes the list itself. A custom dialect that still defines it compiles unchanged; the method is no longer called.

### Fixed

- With `CQL_VALIDATE_SCHEMA_MAPPINGS=1`, a `Bytes` getter on a `blob` column raised a false `SchemaMappingError` (`Slice(UInt8)` does not match `Bytes`); the validator now resolves the alias. The spec suite runs clean with the flag on (the `Article` fixture declared an `Int32` key for an `Int64` model).
- Instance `update!(**attrs)` and `update!(attrs : Hash)` went straight to `Model.update!(self)`, skipping an `OptimisticLocking` model's version check; they now go through the record's own `update!`, so a stale record raises `CQL::OptimisticLockError`.
- `Model.touch_all(ids)` sends one `UPDATE ... IN` per chunk of keys sized to the dialect's bind-parameter limit (less the touched values), instead of one statement binding every id, which failed past the limit. The chunks are separate statements; wrap the call in a transaction to make it all-or-nothing.
- An optimistic-locking update (`update_with_lock!`, and `save`/`update!` on a model with `optimistic_locking`) assigned the version column twice in `SET` (the record's current version and then the incremented one) and also wrote the primary key back. PostgreSQL rejects multiple assignments to one column; the locked update now sets only the incremented version and leaves the key out of `SET`.
- `has_many` declared without `foreign_key:` (`has_many :kids, Kid`) compiles when its methods are used. The default key (`<owner>_id`) expanded to a bare identifier instead of a symbol in the reader, `<name>_count`, `create_<name>` and `preload`, so the model failed with "undefined local variable or method 'owner_id'".
- has_many, has_one and belongs_to inside a namespace failed to compile when the target was a relative path (`has_many :pets, Pet` in `module Blog`): the association check resolved the target from CQL's own module instead of the owner's, so it reported the model as not found even with `foreign_key:`. The target is now looked up through the owner's namespaces (`Blog::Owner::Pet`, then `Blog::Pet`, then the top-level `Pet`), including a target defined after the owner. A relative target that is a top-level model named like a CQL type (for example a `PoolStats` model) is no longer checked against the CQL type. Constants inherited from the owner's superclass or included modules are not searched; name such a target with its full path.
- has_many, has_one and many_to_many declared without `foreign_key:` on a namespaced model kept the namespace in the default key (`Blog::Owner` gave `blog::owner_id`), which failed to compile; so did the many_to_many target key without `association_foreign_key:` (`Blog::Tag` gave `blog::tag_id`). The defaults now use the class name without its namespace (`owner_id`, `tag_id`), as they already did for un-namespaced models.
- `timestamp` and `timestamps` columns are created as `TIMESTAMP` on PostgreSQL and CockroachDB and `DATETIME(3)` on MySQL (millisecond precision, which the `NOW(3)` default of `timestamps` requires). They were created as `DATE`, which dropped the time of day of every stored value: `CQL::Date` is an alias of `Time`, so the type maps' `Date => "DATE"` entry replaced the `Time` one. `date` columns stay `DATE` on every adapter (new `CQL::DateColumn`), and `CQL::SchemaDump` writes `date` for a `DATE` column instead of `timestamp`. SQLite declares timestamps `TIMESTAMP` as before. Tables created before this keep their `DATE` columns; alter them (for example `ALTER TABLE posts ALTER COLUMN published_at TYPE TIMESTAMP` on PostgreSQL) to keep the time of day from now on. PostgreSQL `TIMESTAMP` has no time zone, so a `timestamps` default (`CURRENT_TIMESTAMP`) is the session's local time while CQL writes UTC; run the server or session in UTC to keep them consistent.
- The metrics JSON (`CQL::Performance.metrics.to_json`, `CQL::Performance.export_metrics_as_json`) wrote its non-string nested values as strings: a slow query's `execution_time_ms`, `rows_affected` and `params` (`"execution_time_ms":"150.0"`, `"[JSON::Any(...)]"`), an issue's `details`, an N+1 pattern's `repetition_count`, and every entry of `most_frequent_queries`, `most_expensive_queries`, `highest_error_queries`, `query_patterns` and `error_patterns` (as Crystal's `NamedTuple#to_s`). They are now numbers, arrays and objects, with `Time::Span` values (`avg_time`, `total_time`) in milliseconds. `PerformanceMetrics.to_json_any` passes a `JSON::Any` through and converts a `NamedTuple` to an object.
- many_to_many collections loaded each target with the join row's `id` instead of its own: the target query joined the join table and selected its columns too, so the join row's `id` overwrote the target's. `dependent: :destroy` (on delete or through `clear`) could therefore delete unrelated targets, and `ids`, `includes?` and `delete` on a loaded collection saw wrong ids. The targets are now selected with a subquery, `WHERE <target pk> IN (SELECT <target key> FROM <join table> WHERE <owner key> = ?)`, so the join table's columns never reach them and a target associated twice is loaded once. The join table is no longer in the collection query's FROM: a condition or order on its columns (`post.tags.where { PostTag.table_column(:position) ... }`) now fails; filter the join model (`PostTag.where(...)`) instead. `find`, `find_by` and `exists?` on the collection match on the target's declared primary key, like loading does, instead of `id`.
- has_many, has_one and many_to_many owned by a UUID-keyed model bound the owner's id as a `UUID`, which is not a bindable value, so their queries failed to compile, and since `delete!` applies `dependent:` strategies so did `delete!` on such a model. Collections and the generated lookups now bind ids as text through the new `CQL::ActiveRecord::IdChunks.bound`, as `IdChunks.each` already did, and the has_one reader no longer reads `@id`, which UUID models do not have. has_many and has_one strategies, and many_to_many's join-row cleanup and `:destroy`, work on a UUID-keyed owner. many_to_many `:delete_all`, `ids`, `ids=` and `delete(id)` still assume the owner and its targets share a key type, and writing a UUID foreign key through a model (`create!`, `<assoc>.create`) is still unsupported.
- The generated has_many `<name>_count` returned the count query instead of an `Int64` (it failed to compile when called); it now returns the number of associated rows.
- many_to_many `dependent: :delete_all` with soft-deletable targets soft deleted again the targets already soft deleted, giving them a new `deleted_at` and running their destroy callbacks again. The targets now go through their default scope, as `Target.where(...).delete_all` does: those already soft deleted are skipped, and the rest are soft deleted in bulk unless the target declares destroy callbacks or `dependent:` associations.
- `dependent:` on `has_many`, `has_one` and `many_to_many` did nothing when the parent was deleted: the generated `handle_<name>_dependency` methods were never called, and has_many and many_to_many skipped an association that had not been loaded. `delete!` (and SoftDeletable's `force_delete!`) now applies each declared strategy, reading the associated rows from the database whether or not they were loaded. `:restrict_with_error` raises `RelationError` before the `before_destroy` callbacks and before anything is deleted. The other strategies run after the callbacks, in declaration order, in one transaction with the parent's DELETE: a savepoint inside the caller's transaction when one is open, so a rollback restores everything. A has_many or has_one `:destroy` child whose `delete!` returns false (a callback halted it, or its row was already gone) raises `RelationError`, so the parent is not deleted and the transaction rolls back; a many_to_many target that refuses is kept, unlinked, since it does not reference the owner. The class-level `Model.delete!(id)`, `delete_by!` and `delete_all` still skip the strategies, except on a soft-deletable model, whose `delete!(id)` and `delete_by!` soft delete through the instance `delete!`.
- A `schema.transaction` opened inside another one now runs as a SAVEPOINT on the outer transaction's connection. Before, it checked out a second pooled connection and committed independently: an inner block's writes survived when the outer transaction rolled back, it held two connections at once, and on SQLite it failed with `database is locked`. An inner `DB::Rollback` or error now undoes only the inner block, and nesting no longer needs a second pool slot (also on `CQL::Postgres::EngineSource`). Code that relied on the inner block committing independently must now run it on a separate fiber/connection. crystal-db allows one open savepoint per transaction, so `Model.transaction(tx)` with the outer `tx` inside an open nested `schema.transaction` now raises; use the inner block's transaction instead.
- `Model.query...count` ignores `order` (it emitted `COUNT(*) ... ORDER BY`, a wasted sort that PostgreSQL rejects for ungrouped columns) and respects `limit`/`offset`: `limit(2).count` now returns at most 2 by counting a derived table (`SELECT COUNT(*) FROM (...) AS counted_rows`); before, LIMIT/OFFSET applied to the single aggregate row, so `limit(2).count` returned the full count and `offset(2).count` returned 0. The limited count runs on the query's pinned executor, selects only the primary key (or the counted column) inside the derived table, and `QueryBuilder#count_query` returns the statement `count` runs.
- has_many and many_to_many collections no longer change their own query: `reload`, `count`, `find`, `find_by`, `where`, `limit`, `offset` and `order` run on a copy. Before, each call added another `fk = ?` to the stored query, `count` left `COUNT(*)` behind (so a later `reload` failed with a missing column), and `limit`/`offset`/`order`/`where` stuck to every later call on the same collection. `Collection.new` and `ManyCollection.new` now scope the query they are given to the parent themselves (many_to_many through the join table), lazily on first use, so passing an unscoped `query:` no longer returns other parents' rows. Pass the base query unscoped: for `Collection` an already scoped query still works but carries the predicate twice; for `ManyCollection` a query that already joins the join table raises a duplicate table error.
- many_to_many collections: `delete_all` and `nullify_all` now delete this parent's join rows and return how many were removed, keeping the associated records (they may belong to other parents; use `clear` with `dependent: :delete_all` or `:destroy` to remove them). Before, both were inherited from has_many and always raised, because they filtered the target table by the join table's foreign key.
- The many_to_many association query no longer assumes the target's key column is named `id`; it now uses the target model's `primary_key_column` (see `db_context ... primary_key:` under Added).
- many_to_many `clear_with_destroy` (used by `dependent: :destroy`) now destroys the associated records when the collection was never loaded. Before, it removed only the join rows: the records it meant to destroy were the same array that clearing the join rows emptied.
- `CQL.build_schema` now compiles and runs: the table-definition block runs against the new schema (it previously failed with `undefined method 'table' for top-level`), and the SQL logging setup calls `CQL::Performance.enable_sql_logging` (the development default used a method that did not exist).
- `CQL.build_schema` opens the database through `config.full_db_url`, so `pool.*`, `ssl.*`, SQLite/MySQL/PostgreSQL settings and `adapter_options` now reach the connection. URL parameters still win.
- The native PostgreSQL driver accepts and ignores the `auth_methods` URL option that `CQL.configure` adds for the `pg` shard, instead of sending it to the server as a startup parameter (which PostgreSQL rejects). This matters now that `CQL.build_schema` opens through `config.full_db_url`.
- `config.sql_logging` is now unset until you assign it: unset follows the environment (on in `development` unless `CQL_NO_SQL_LOG` is set, evaluated when queried), and `config.sql_logging = false` turns it off in development.
- `config.pool_size=` updates `config.pool.size` and keeps `pool.initial_size` and `pool.max_idle_size` from exceeding it.
- `config.sql_logging_async` is unused and kept only for compatibility.
- Indexes declared on a table (`index [...]`, `add_index`, or `index: true` on a column) are now created: `table.create!` and `schema.build` run one `CREATE INDEX IF NOT EXISTS` per index after `CREATE TABLE` (plain `CREATE INDEX` on MySQL, which has no `IF NOT EXISTS` for indexes). Previously they were only kept in memory. `index`/`add_index` accept an optional `name:`, and index names longer than 63 characters raise `ArgumentError`.
- **MySQL:** because of that, calling `table.create!` or `schema.build` again on a table with declared indexes (including `index: true` columns) now raises a duplicate key name error, and `schema.build` stops at the first failing statement. Call them once per database, or create indexes with `create_index` in a migration.
- The default index name is now `idx_<table>_<columns>` (e.g. `idx_users_name_email`) instead of `idx_` plus the first four characters of each column, so indexes on same-named columns of different tables no longer collide.
- The migrator's `schema_migrations` table no longer declares a separate index on `version`; its `UNIQUE` constraint already indexes it.
- Because `CQL.build_schema` now applies `full_db_url`, SQLite connections opened through it use the configured defaults (`journal_mode=wal`, `synchronous=normal`, `foreign_keys=1`, `busy_timeout=5000`); set `config.sqlite.*` to change them.

- Building a query no longer rewrites the table's primary key. It read `Table#primary`, which re-declared a default `id` (Int32) key, so after the first select `create_sql` declared an `Int64` key as `INTEGER`, a key not named `id` gained a second `id` key, and a keyless or plain-`id` table gained an `id` key. Query building and foreign keys use the new non-mutating `Table#primary_key`; a bare `primary` in a table block still declares the default key, and `primary(name, type)` now requires the name.
- `Model.create!(record)` with an Int32 primary key on PostgreSQL and CockroachDB no longer raises `DB::ColumnTypeMismatchError` (the `RETURNING` key is read as `INT4`).
- CQL's native PostgreSQL layer (`CQL::Postgres`) compiles against crystal-db 0.15, which made `DB::Connection#driver_name` abstract (`CQL::Postgres::Connection#driver_name` returns `"postgres"`). The SQLite, MySQL and `pg` drivers CQL's own specs use still need releases that support db 0.15. `script/check_db_compat` and the `crystal-db compatibility` workflow (also weekly, against the latest db) compile the native layer against crystal-db 0.13.1, 0.14.0, 0.15.0.
- `Model.create!(**fields)` and `Model.create!(attrs)` on PostgreSQL and CockroachDB now read the new key through `RETURNING` (as `create!(record)` already did for Int64 keys) instead of `last_insert_id`, which crystal-pg always reports as 0, so the row was inserted but `find!(0)` raised `DB::NoResultsError`. Int32 keys are read as `INT4`.
- Subqueries (`IN (SELECT ...)`, `EXISTS`, `INSERT ... SELECT`) no longer discard the parameters bound by the enclosing query (SELECT, UPDATE and DELETE), and PostgreSQL `$n` numbering now continues across them.
- Multi-row `INSERT` on PostgreSQL numbers each row's placeholders (it emitted `($1,$2),($1,$2)`); rows are aligned by column name and rows with a different column set raise `ArgumentError`.
- `OFFSET` without `LIMIT` is no longer dropped (bare `OFFSET` on PostgreSQL, `LIMIT -1` on SQLite, maximum `LIMIT` on MySQL).
- Block DSL qualifies columns with the table alias (`from(customers: :c).where { c.city == ... }`).
- `Update#where` / `Delete#where` AND with earlier conditions instead of replacing them.
- `QueryBuilder#having` builds a `HAVING` clause (it called `where`); `reverse_order` and `unscope` work; aggregates, `ids` and `reorder` no longer alter the builder they are called on.
- `mysql://` URIs are accepted by `Schema` (an empty host is rejected).
- `QueryBuilder#pick` no longer alters the builder it is called on; `Model.having` accepts implicit-self blocks.

- Connection pool configuration consistency
- Transaction rollback handling
- Error context in exception messages

### Security

- Mass assignment can no longer re-point a record at another row: `attributes(...)`, instance `update!(attrs)` and `Model.from_hash` ignore the primary key, so request params carrying an `id` (or a custom key column) do not make a following `save`/`update!` overwrite that row.
- SQL logging (`CQL::Performance.enable_sql_logging`, `CRYSTAL_ENV=development`, or `CQL.build_schema` with `sql_logging` on) no longer writes bound parameter values, which often hold personal data. `config.logging.include_params` was never read; it now controls both the `Parameters:` line of a logged statement (including slow statements logged at warn or error) and the `Params:` part of a failed statement's error log, and it defaults to `false` in every environment (it was `true`). When logged, a failed statement's values are now rendered like the `Parameters:` line (truncated at `logging.max_param_length`), and both escape newlines and other control characters so a value cannot start a forged log line. Opt back in with `CQL::Performance.configure(&.logging.include_params=(true))`. `SQLFormatter.new` takes `include_params:` (default `false`) and `configure(include_params:)`, so a formatter built without it no longer prints the values; `SQLFormatter#loggable_params` returns the values as they would be logged, or `nil` when hidden.
- The metrics JSON (`CQL::Performance.metrics.to_json`, `CQL::Performance.export_metrics_as_json`) no longer exports the bound values of slow queries: each entry of `top_queries.slowest_queries` has no `params` key unless `config.logging.include_params` is on. `QueryData#to_h` takes `include_params` (default `false`) and `PerformanceMetrics::TopQueries.new` an optional fifth `include_params` argument; `PerformanceMetrics.from_components` reads it from `config`. The in-memory `QueryData#params` is unchanged.
- DDL identifiers that cannot be bound as parameters are now validated: index, foreign key, unique/check constraint names, rename targets and foreign key table/column names must match `[A-Za-z_][A-Za-z0-9_]*` (`DROP INDEX` also accepts one `schema.` qualifier). Anything else raises `ArgumentError` instead of being spliced into SQL. Names with other characters (hyphens, dots, spaces, non-ASCII) previously produced broken unquoted SQL.
- Aggregate aliases (`count(:id, as: "n")`) are validated the same way.

- SQL injection prevention in query builder
- Parameterized query support
- Prepared statement usage by default

## Migration Guide

### Deprecated parameters

#### Deprecated `cascade` Parameter

**Deprecated:**

```crystal
has_many :posts, foreign_key: :user_id, cascade: true
```

**Preferred:**

```crystal
has_many :posts, foreign_key: :user_id, dependent: :destroy
```

**Dependency Options:**

- `:destroy` - Destroy associated records (runs callbacks)
- `:delete_all` - Delete associated records (no callbacks)
- `:nullify` - Set foreign key to NULL (default)
- `:restrict` - Prevent deletion if associations exist
